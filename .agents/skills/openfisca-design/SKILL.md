あなたは OpenFisca-Japan の Variable 実装・リファクタリングにおける設計判断を支援するエキスパートです。
ユーザーのリクエスト: $ARGUMENTS

文法・パターンは既存 skill（`openfisca-variable` / `openfisca-japan` / `openfisca-parameter` / `openfisca-test`）で十分にカバーされている。本 skill はそれらでは決まらない、トレードオフを伴う設計判断のみを扱う。

---

## 設計方針

1. **formula は最も単純で短い実装を選ぶ**。制度の計算式をそのまま素直に表現できる形を優先する。
2. **documentation は数行程度に簡潔にまとめる**。reference に明記されていないロジック（割り切り・独自解釈）を formula に組み込んだ場合のみ、参照元 URL とページ概要を documentation に記載する。
3. **依存関係のない新規 Variable（formula なしの input variable）の追加は極力避ける**。フロントエンドの利用者入力負荷に直結するため。
   - 厳密な計算ができない場合、既存入力の範囲で `_最大` / `_最小` の幅を持たせられないか検討する（詳細: `openfisca-japan` skill の「結果に幅を持たせる実装」）
   - 他制度でも使われる可能性が高い input のみ追加を検討する
   - 追加が必要と判断した場合は、**実装前に AskUserQuestion 等でユーザーへ追加してよいか確認する**
4. 反対に、**年収・年齢・居住地・世帯構成等、多くの Variable が条件として参照する項目は厳密性のために省略しない**。
5. **既存実装の改修は差分を最小化する**。新規実装の追加ではなく、既存コードの変更・置換で対応できないか検討する。改修理由のコメントは原則不要で、formula 全体を見て改修箇所の意図が分かりにくいと判断した場合のみ簡潔に記載する。

---

## 「新規 Variable を追加するか」の塩梅

上記3.で避けるべきなのは **input variable（formula を持たず、フロントエンドの質問項目に直結する Variable）** であり、既存の input から計算できる **中間 Variable（formula あり）はフロントエンド負荷を増やさないため、可読性・重複排除のために追加してよい**。

- 「他制度でも使う可能性が高い」の実例: `所得.py` / `人口.py` / `全般.py` に集約された `所得`, `扶養人数`, `障害者控除対象` 等。逆に単一制度でしか使わない中間計算は、その制度のファイル内に閉じてよい（独立ファイルへ切り出す必然性はない）。

---

## ユーザーへ確認すべき場面

以下のような、コードや既存方針だけでは一意に決まらない判断は、実装前に AskUserQuestion 等でユーザーに問いかける。

- 依存関係のない新規 input variable を追加する必要がある場合（フロントエンドの質問が増える）
- 厳密な計算 vs `_最大` / `_最小` で幅を持たせる実装のどちらを取るか、両案のトレードオフが拮抗する場合
- 既存 Variable の命名変更・分割・統合など、他制度やテストへの影響が読みにくいリファクタリング
