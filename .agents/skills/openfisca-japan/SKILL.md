## 1. フロントエンド連携上の制約

- 見積もり結果ページに表示する制度の Variable は **`entity = 世帯` にする必要がある**（フロントエンドが世帯単位でしか結果を受け取れない仕様のため）
  - 個人に支給される手当であっても、最終的な金額 Variable は世帯単位で実装する
  - 個人ごとの条件は `対象世帯.members(...)` で世帯員単位に計算し、`対象世帯.sum(...)` 等で世帯単位に集計してから返す
  - 個人単位のままでよい中間計算用 Variable（依存先）は `entity = 人物` でも構わない
- フロントエンドを先行開発したい場合は、**バックエンド側に空の Variable（formula なしの入力変数）を先に用意**しておく
  - 未定義の Variable を参照する制度がフロントエンドにあると API がエラーを返すため
- API に JSON を POST する際は、`formula` で算出される中間値を入力すると **エラーになる**
  - YAML テストでは中間値（例: `所得`）を直接指定してもテストが通るが、実際の API リクエストでは元となる入力（例: `収入`）を渡す必要がある
  - フロントエンド実装時はこの違いに注意する
- API の日付は `YYYY-MM-DD`（0埋め2桁）で送る必要がある。テスト用 API は0埋めなしでも動くが、本番 API は0埋めしないとエラーも出さずに誤計算する
- `entities.py` でエンティティ名（`世帯`/`人物` 等）を変更した場合、`openfisca_japan/situation_examples` 配下の JSON も合わせて修正が必要（漏れると `SituationParsingError` でサーバーが起動しなくなる）

## 2. 複数世帯対応でのつまずきやすい点

このリポジトリでは複数世帯を一括計算するため、単一世帯でしか動かないコードは CI (`make check-style`) で検知されうる。基本ルール（if 文禁止・`+`/`*` で `or`/`and` を代替・`household.sum`/`household.max` を使う）は `openfisca-variable` skill を参照。ここでは **見落としやすい派生的な注意点** のみ記載する。

### 演算子の優先順位に注意
`*`（and 相当）は `+`（or 相当）より優先順位が高いため、意図と異なる評価順になりやすい。

```python
# 意図: (A > B) and (C < D)
# NG: かっこが無いと `A > (B * C) < D` と解釈されてしまう
条件 = A > B * C < D

# OK: 明示的にかっこでくくる
条件 = (A > B) * (C < D)
```

### 片方が数値配列だと算術加算に化けるバグ
`+`/`*` は bool 配列同士なら OR/AND として働くが、**片方が数値の ndarray だとエラーにならず普通の算術演算になってしまう**。型が意図通り bool（0/1）かどうかを都度確認すること。

### `np.min`/`np.max` を2つの式の比較に使う場合
値の集計（世帯ごとの合算等）ではなく、**2つのスカラー式のうち小さい方/大きい方を選ぶ**用途で `np.min`/`np.max` を使うのは許容される（`household.sum`/`household.max` の対象は世帯員配列の集計であり、用途が異なる）。ただしこの用法は独自 lint ルールに引っかかるため、行末に `# noqa: TID251` を付けて抑制する。

```python
a = np.max([生活扶助基準1 * 0.855, 生活扶助基準2], axis=0) + 経過的加算  # noqa: TID251
```

### CI の複数世帯チェックに引っかかった場合
`make check-style`（PR 時に GitHub Actions で実行）で「複数世帯の場合に正しく計算できないため...」というエラーが出た場合は、上記のパターンに沿って実装を修正する。lint の誤検知で意図的に無視したい場合は `# noqa: {ルール名}` を付ける。

## 3. インデックス参照は `np.select` / `np.clip` 経由にする

`扶養人数` のような Variable の計算結果（ndarray）を**そのまま配列の添字として使うと、複数世帯入力時に型が合わず計算できない**。

```python
# NG: 複数世帯のとき計算できない
所得制限限度額 = 児童育成手当.所得制限限度額[扶養人数]

# OK: np.select で扶養人数ごとに値を選択する
所得制限限度額 = np.select(
    [扶養人数 == i for i in range(6)],
    [児童育成手当.所得制限限度額[i] for i in range(6)],
    -1).astype(int)
```

- 選択肢が多い場合（0〜9人など）は `np.clip` で値を範囲に丸めてからインデックスに使う方法もある
  ```python
  所得制限限度額 = np.array(特別障害者手当.所得制限限度額.本人)[np.clip(扶養人数, 0, 9)]
  ```
- `np.select` の condlist は **最初に該当した条件で決まる**（`if/elif` 相当）
- 該当なしのデフォルト値は `None` ではなく `-1` 等の整数にする（`.astype(int)` できるようにするため）

## 4. CSV ファイルの参照

金額表など項目数が多いデータは Parameter YAML よりも **可読性の高い CSV** で `openfisca_japan/assets/` 配下に置くのが慣例。

- 標準ライブラリの `csv` はリスト形式で返るため ndarray と型が合わず計算に使えない。**`np.genfromtxt` で読み込む**
- 列名（ヘッダー）はそのままでは使えないため、列の意味に対応するインデックスを別途 `np.select` 等で生成する
- ファイル読み込みは `@cache` デコレータでキャッシュし、formula 呼び出しのたびに読み直さないようにする

```python
@cache
def 支給限度額_学年制表():
    return np.genfromtxt(COUNTRY_DIR + "/assets/福祉/育児/高等学校等就学支援金/支給額/支給限度額_学年制.csv",
                         delimiter=",", skip_header=1, dtype="int64")[:, 1:]
```

- **out of bound 対策**: デフォルトインデックスを `-1` にしても NumPy 上は「最後の要素」が取得されてしまい、条件外の入力でも値が返ってしまう。**取得後に改めて対象条件を満たすか確認して掛け合わせる**こと。

```python
支給金額 = 支給限度額_学年制表()[履修種別インデックス, 運営種別インデックス]
# NOTE: out of bound対策で条件外でも値が取得できてしまうため、改めて対象条件を確認
支給対象者である = 高校生である * (履修種別 != 履修種別パターン.無) * (運営種別 != 運営種別パターン.無)
return 支給対象者である * 支給金額
```

## 5. 年内の特定日付を参照する

「当年12月31日時点の年齢」のように、期間内の特定日付の値を参照したい場合は `period()` で日付を決め打ちで再構築する。

```python
該当年12月31日 = period(f"{対象期間.start.year}-12-31")
年齢 = 対象人物("年齢", 該当年12月31日)
```

- `所得` のように本来 `YEAR` で決まる値でも、日次の手当計算から参照できるよう **あえて `DAY` で `definition_period` を定義する**ケースがある（`YEAR` のままだと `DAY` 定義の Variable から参照できないため）

## 6. Variable 名の衝突回避（このリポジトリでの実例）

Variable 名はリポジトリ全体で一意である必要がある（`openfisca-variable` skill 参照）。このリポジトリでは以下のように**制度領域を示す接頭辞**を付けて衝突を避けている。

- 所得税と住民税で同じ制度でも異なる Variable 名にする（例: `住民税障害者控除`, `住民税ひとり親控除`, `住民税配偶者控除` など、`住民税.py` 内は軒並み `住民税` 接頭辞）
- 自治体固有の制度（`variables/東京都/...` 配下等）も、他自治体で同名の制度を追加する際に衝突しないよう接頭辞（例: `東京都_`）を検討する。ただし現状のコードでは `東京都/福祉/児童育成手当.py` の `児童育成手当` のように接頭辞なしで実装されている例もあるため、**新規追加時に同名の制度が他にないか確認した上で判断する**
- 接頭辞を付ける場合は**その領域の Variable すべてに統一して付ける**（一部だけ付けるのは避ける）

## 7. 結果に幅を持たせる実装（`_最大` / `_最小`）

詳細な症状や状況確認が必要で入力だけでは一意に算出できない制度は、`{制度名}_最大` / `{制度名}_最小` という2つの Variable を作り、最小値・最大値の範囲で結果を返す（実例: `特別障害者手当_最大`/`_最小`, `障害基礎年金_最大`/`_最小`, `傷病手当金_最大`/`_最小`）。

- **`_最大`**: 条件を緩く（広く）取った場合の結果。OR 条件を広く取る、対象外となる例外条件を無視するなど
- **`_最小`**: 条件を厳しく（狭く）取った場合の結果。AND 条件を厳しく取る、除外条件も反映するなど

```python
class 特別障害者手当_最大(Variable):
    documentation = "厳密な判定には詳細な症状が必要なため、各種手帳等級から推定可能な最大値を算出"
    def formula(...):
        障害条件 = 身体障害条件 + (精神障害条件 + 知的障害条件)  # ORを広く取る

class 特別障害者手当_最小(Variable):
    def formula(...):
        障害条件 = 身体障害条件 * (精神障害条件 + 知的障害条件)  # ANDで厳しく取る
```

必要な入力項目が多くフォームの負荷が高い場合、「入力を増やして一意に特定する」か「入力を絞って `_最大`/`_最小` の幅で返す」かを設計時に両案比較して選ぶ。

## 8. 実装スコープの割り切り方針

都道府県・自治体ごとに条件が大きく異なる、または現物給付・就労支援など金額換算できない制度に対しては、以下のいずれかで割り切って実装する。

- **金額算出が難しい制度は「対象者である」boolean Variable のみ実装**し、支給額は算出しない（例: `特定疾病療養の対象者である`, `重度心身障害者医療費助成制度の対象者である`）。命名は `〜である`/`〜がいる`/`〜の対象者である` のような自然文にする（固定の suffix 規則があるわけではない）
- **対応済みの入力のみを対象範囲とする**（例: 障がい者手帳・特別児童扶養手当のみ対応し、他の証明手段は非対応と明示）
- 所得を条件に使う制度では、**実費ベースの控除（雑損控除・医療費控除等）は対象外**にする（フォーム入力の負担が大きいため）。社会保険料も実額ではなく `所得.社会保険料相当額` のような一律相当額を使う
- 割り切った範囲は `documentation` に明記する（例: 「厳密な判定には詳細な症状が必要なため、〜から推定可能な最小値・最大値を算出」）
- 例外的なケースを無視する場合も `NOTE`/`TODO` コメントで明示しておく（将来の改善余地として残す）

## 9. 世帯主の決め方

このリポジトリでは、**所得が最も多い世帯員を世帯主とする**という割り切りで実装している（厳密には世帯主は所得の多寡のみでは決まらないが、便宜上の扱い）。

```python
所得降順 = 対象人物.get_rank(対象人物.世帯, -所得)
世帯主である = 所得降順 == 0
```

- 複数人が同率の場合の扱いも含め `get_rank` の挙動に従う（同率は index 順で決着する）
- 配偶者を区別したい場合は `世帯.親` の role を条件に加える（例: `(所得降順 == 0) * 対象人物.has_role(世帯.親)`）（実例: `openfisca_japan/variables/所得.py` の同一生計配偶者関連 Variable）
- 実例: `openfisca_japan/variables/災害/支援/災害援護資金.py`, `openfisca_japan/variables/所得.py`

## 10. entity のロール定義

`世帯` entity の role は以下の3つのみを使う（`entities.py` 参照）。それ以外の role は定義しない。

- **`親`**: 自分と配偶者（子供がいない場合の大人も「親」role とする。最大2人）
- **`祖父母`**: 親の親（世帯内のそれ以外の個人）
- **`子`**: 親と同居している子供

Variable の formula で「自分または配偶者かどうか」を判定したい場合は `対象人物.has_role(世帯.親)` を使う。「祖父母」「子」も同様に `対象人物.has_role(世帯.祖父母)` / `対象人物.has_role(世帯.子)` で判定する。

## 11. YAML テストでの中間変数の直接指定

YAML テストでは、`formula` で算出される中間変数（ユーザーが直接入力する項目ではない Variable）であっても、`input` に直接値を指定してテストケースを簡略化できる（例: `収入` から算出される `所得` を直接 `所得: 10000000` のように指定する）。

- これにより、上流の入力（`収入` や各種控除の条件）を全て揃えなくても、対象の Variable の挙動だけをピンポイントでテストできる
- ただし、**実際の API リクエスト（フロントエンド連携）では中間値の直接指定はエラーになる**（[1. フロントエンド連携上の制約](#1-フロントエンド連携上の制約)を参照）。YAML テストで通ったからといって API でも同じ入力が使えるとは限らない点に注意する

## 12. 開発ツール・デバッグ

- **Variable 依存関係の可視化**: `python tools/dependency_graph/dependency.py`（要 Graphviz）で `tools/dependency_graph/dependency_graph.png` を生成。`A -> B` は A の formula が B を参照していることを表し、依存先のない Variable は青色で表示される。実装方針を見直す際に活用する
- **CSV からの YAML テスト自動生成**: `cd tools/make_tests && bash generate.sh` で `openfisca_japan/tests/generated` 以下にテスト YAML を生成できる。生成形式を変えたい場合は `tools/make_tests/mylib/mymodule` 配下を修正する
- **variables 修正後は `make build` してからテストする**（ビルドしないと修正が反映されない）
- テスト成功時は `variables/*.py` 内の `print` 出力は表示されない。失敗時（または例外発生時）は表示されるため、**デバッグ時はわざと例外を発生させると標準出力が見られる**
- YAML テストの小数値は `対象世帯.members` 等で読み出す際、`value_type = float` でも **0.5 単位に丸められる**（閉区間 `[-0.25, 0.25] → 0`、開区間 `(0.25, 0.75) → 0.5`）。誤差の出やすい期待値はこれを踏まえて設定するか `absolute_error_margin`/`relative_error_margin` を使う
